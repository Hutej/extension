- PARITY BAR (Answer.txt Q4): judge a transformation against the ORIGINAL
  page — no clipped content, no hidden content, responsive after resize,
  reading order preserved, interactive elements still work. → Folds into
  the R3 pass bar verbatim.
- WRAPPERS (Answer.txt Q8): a wrapper is disposable layout scaffolding, not
  semantic DOM — the child stays identical (no listener/state/ID changes);

- READING ORDER (Answer.txt Q9): visual order must follow DOM order unless
  the user explicitly requests otherwise — no CSS `order`, no arbitrary

- DON'T-RELAYOUT LIST (Prompt Output D2): never blindly relayout shadow DOM,
  virtualized lists, carousels, editors, canvas, SVG, maps, video players,
  JS-controlled components; never replace an existing flex/grid container —
  wrap it or work at a higher semantic boundary. → R5 media + general.
- FLUID TOKENS (Prompt Output D3): author typography/spacing as
  clamp()-based steps applied at SEMANTIC levels (body, headings, captions),
  never on every nested element (compounded inheritance). Concrete pattern:
  --step-1: clamp(1.25rem,1.1rem+0.8vw,1.6rem); --space-m: clamp(16px,2vw,24px).
  → Prompt authoring guidance (T6+).
- TEST-SITE ORDER (Answer.txt Q2): documentation-style sites first
  (MDN/Wikipedia/GitHub docs); YouTube/BBC are stress tests, not
  architecture validation. Already our rule 18 practice.

0. THE DIAGNOSIS (evidence-based, from the reports)
======================================================================

WHAT IS PROVEN AND STAYS (do not touch, do not rewrite):
- Reversal: on/off byte-identical on MDN + Wikipedia + HN (PHASE2, 4/4).
- Integrity: checkLayout + auto-undo + circuit breaker, baseline-diffed
  (PHASE3, adversarially reviewed).
- Identity: structural descriptors, twin-refusal, 64/64 (PHASE4 + patch).
- Continuity: reload + SPA + second-article survival (PHASE5, 44/44).
- Emit: USER-origin insertCSS, whole-sheet !important retry (T4),
  textEffect no-op detection (T5).
- Design snapshot: 214-272 chars, 4-30ms, proven to change model behaviour
  (T1 A/B: WITH = done in 6 steps, WITHOUT = budgetExhausted).

THE FOUR REAL BOTTLENECKS (in order of measured impact):

B1. THE BRAIN IS TOO WEAK.
    glm-5.3-flash, reasoning_effort:'low', temp 0, 4k max tokens, 30s
    call timeout, via Cloudflare Workers AI.
    Evidence:
    - T4: 17 of ~25 authored acts refused (selector hallucination).
    - T5: 96 of 166 paid calls were re-refinement churn.
    - T6: 43 and 54 paid calls hitting the 300s ceiling on 2 of 10 runs.
    - 52 parse-failure files: timeouts, empty responses, transport outages.
    - T1: transformation "too subtle" (#f6f6ef -> #faf6ef, invisible).
    - T2: hn-premium never completed in 4 runs pre-budget-fix;
      post-fix 27 acts, 4 applied, ~40 calls decorating.
    A flash model with low reasoning effort cannot be a designer + CSS
    author + DOM navigator at once. Every T-phase gap (timidity, no-ops,
    churn, hallucinated selectors, timeouts) is downstream of this.

B2. THE MODEL IS BLIND TO ITS OWN OUTPUT.
    No look/effect feedback in the loop. Verification is by proxy
    (assertApplied computed-style, textEffect, contrast scan) — the agent
    itself never learns WHAT VISIBLY CHANGED after an act.
    Evidence:
    - T5: hn-body shipped done with byte-identical screenshots
      (body rule shadowed by td rules). textEffect fixed the text case only.
    - T6: wiki-content-area byte-identical no-op shipped as done
      (spacing/geometry case — textEffect does not cover it).
    - Churn: without effect feedback the model cannot converge, so it
      re-refines (96/166 calls in T5).
    Where intelligence "fades": mid-run. Turn 1-3 reasoning is decent;
    turn 5+ is reasoning in the dark.

B3. SPEED = MODEL LATENCY x CALL COUNT. Local code is fast.
    All local gates: 4-94ms. Model calls: 8-50s. Successful runs: 11-90s.
    Churn runs: 300s. Fewer, smarter calls on a better brain is faster
    than many flash calls: hn-dark done in 11.6s / 4 calls proves the
    ceiling is good when the model converges.

B4. STOP DISCIPLINE IS UNSOLVED.
    No contract for "declare intended visible effect -> stop when
    achieved". hn-premium spent ~40 calls decorating before the ceiling
    stopped it. The 80-step/300s budget enabled marathons instead of
    forcing convergence.

IS "AN AGENT THAT LIVES IN YOUR BROWSER" TRUE?
    Yes. The loop runs in the extension's service worker; every tool
    executes in the page's content script; all state (journal, ops,
    persistence) is local chrome.storage; the site's backend is never
    touched. The only remote element is the model inference API call —
    which is equally true of Mirage and every competitor. "Lives in the
    browser" = execution and actuation are local. The claim is honest.

WHY MIRAGE LOOKS BETTER (from their own site):
    1. Frontier-tier hosted brain (their copy: "SOTA agent").
    2. Visual feedback closing their loop (they preview and let you
       refine — i.e., a human in the loop as the vision system).
    3. Product UX we don't have yet: Preview -> Save -> Gallery -> share
       link, userscript import.
    4. Their actual demonstrated scope is NARROWER than our dream:
       hide Shorts, calmer Gmail, bigger titles, denser feed. They are
       winning the 80% we already do — with a better brain and better UX.
    Lesson: do not chase the 20% (3D, workflows) yet. Win the 80% on one
    site with a real brain and a closed feedback loop.

PHASE R0 — BRAIN UPGRADE BENCHMARK (no architecture change)
----------------------------------------------------------------------
GOAL: replace B1 with data, not opinion.

WHAT TO DO
1. Add RV_MODEL_STRONG variants + reasoning_effort + max_completion_tokens
   to core/config (already env-driven: core/config/index.ts:14,39 —
   mostly .env + small config edits).
2. Re-run, unchanged: tests/design-t5 baseline goals (10 typography runs)
   and the T6 spacing goals (10 runs) — 20 runs per candidate model.
3. Measure per run: status, wallMs, paidCalls, actsApplied/actsAuthored,

   timeouts/empty responses, by-eye 1-5 quality score (vision QA in

   like T6).
4. Compare against the recorded baselines: T5 (166 calls, 4-299s,

DELIBERATE FAILURE CASE: hn-premium (never completed in any T2 variant)

DONE MEANS: a winner with fewer calls, zero no-ops shipped, faster wall

----------------------------------------------------------------------
PHASE R1 — EFFECT FEEDBACK: close the model's eyes (kills B2)
----------------------------------------------------------------------
GOAL: after every act, the model receives, in words, WHAT VISIBLY
CHANGED — and is told plainly when nothing did.

TOOL: diffVisual (verify tier, auto-dispatched after every successful
act, exactly like checkLayout is today — not a model choice).

IMPLEMENTATION
1. Before the act, capture a cheap baseline: sampled leaf elements
   (reuse T5 textEffect's stride sampler, act.ts:169-198) — for each:
   {rect, display, visibility, computed color/background/border,
   font props}. Cap: ~120 leaves, prioritized to the acted selector's
   subtree + main content.
2. After the act (post settle/transition wait — reuse waitForTransition,
   act.ts:125), re-measure the same leaves.
3. Summarize DELTAS into <=400 chars, buckets only, no absolute px
   written back anywhere (rule 6 — this is observation, reported as
   deltas/categories):
   - geometry: "N elements resized (>10%), M moved, K collapsed"
   - paint: "text color changed on ~N leaves; backgrounds shifted on M"
   - visibility: "N leaves now hidden"
   - type: reuse textEffect's changed:count line
   - net: "VISIBLE CHANGE" or "NO VISIBLE CHANGE" (the money line)
4. Surface in the act's tool result + journal. "NO VISIBLE CHANGE" is an
   ERROR MESSAGE THAT NAMES AN ALTERNATIVE (rule 13): "No visible change.
   The rule applied but is shadowed — target the elements that actually
   paint this content (call findElements on the region), or strengthen
   the selector."
5. Generalizes T5's textEffect (text is one bucket); textEffect retires
   into it.

TESTS
- Deliberate no-op failing case (T5's hn-body scenario on fixture):
  diffVisual must report NO VISIBLE CHANGE.
- Deliberate visible case: reports the right buckets.
- Budget: diffVisual itself must stay <50ms (it's stride-sampled).
- Real site: Wikipedia dark-theme run — model receives effect feedback
  every act.

DONE MEANS: a no-op transformation cannot ship as done (T5+T6 class
dead), and the model's next-turn reasoning references what actually
happened (churn drops — measure calls-to-convergence before/after).

----------------------------------------------------------------------
PHASE R2 — STOP DISCIPLINE + BUDGET RE-TIGHTENING (kills B4)
----------------------------------------------------------------------
GOAL: the model stops when the goal is visibly achieved; budgets shrink
back from marathon-enablers to safety rails.

IMPLEMENTATION
1. Prompt protocol (agent/prompt.ts): before each act the model's
   reasoning must state the intended visible effect in one clause
   ("story titles will be ~20% larger and sans-serif"). diffVisual (R1)
   then confirms or denies. Two consecutive confirmed effects without a
   remaining sub-goal -> done.
2. Convergence guard in the loop: if the last act reported NO VISIBLE
   CHANGE and the model re-attempts the same selector+property family,
   that turn's tool error escalates ("this is attempt 3 on the same
   target; re-scope or giveUp"). No new budget machinery — one counter.
3. Re-calibrate with R0+R1 data: expected maxSteps ~20-24, maxWallMs
   ~120-150s for standard runs. 80/300s stays only as the hard runaway
   ceiling. The class defaults in budget.ts (12/60s) get deleted —
   they're dead and misleading (config is the truth).

DELIBERATE FAILURE CASE: hn-premium decorating behavior must now end in
done (or a justified giveUp) well before 20 steps.

DONE MEANS: T6's 43/54-call exhaustions become impossible; wall clock
median on the MVP corpus lands under 60s.

----------------------------------------------------------------------
PHASE R3 — ONE-SITE MVP BENCHMARK (the demo)
----------------------------------------------------------------------
GOAL: prove, on Wikipedia only, the product sentence: "It reshapes the
live page, lets you refine it, and saves the version you want."

THE 10 MVP REQUESTS (Wikipedia, fresh wording every run — rule 17):
 1. Turn this article into a dark reading theme.       (color)
 2. Make this read like a magazine spread.            (typography+layout)
 3. Give the page breathing room.                      (spacing)
 4. Hide everything that isn't the article.            (hide+heal)
 5. Make the table of contents a compact sidebar rail. (recompose-lite)
 6. Calmer colors, less blue.                          (color)
 7. Bigger, clearer headings.                          (type hierarchy)
 8. Make the references section collapsible.           (insert+behavior-lite)
 9. Make it look and feel premium.                     (coordinated)
10. Undo everything, then redo items 1 and 3 only.    (reversal+continuity)

PASS BAR PER REQUEST (all must hold):
- intent satisfied BY EYE (vision QA in words + your eye — rule 19)
- no NO-VISIBLE-CHANGE shipped
- PARITY vs the ORIGINAL page (senior advice, kept): no clipped content,
  no hidden content beyond the request, reading order preserved,
  interactive elements still work
- on/off restores byte-identical (F3 harness, already exists)
- survives reload (F4 replay, already exists)
- survives resize 1440 -> 380 -> 1440 (resize proof, already exists)
- wall clock < 60s, paidCalls < 12
- zero checkLayout regressions introduced (baseline-diffed, exists)

REPORT FORMAT: table (request x pass-bar), before/after PNGs, vision-in-
words, calls/wall/undo counts, and the one thing that looks worst.

DO NOT proceed to R4 until 8/10 pass. If the brain is still the wall,
this is where it becomes undeniable — the benchmark is the argument for
D1c.

----------------------------------------------------------------------
PHASE R4 — CREATE & INSERT WITHOUT BREAKING (user-requested gap #1)
----------------------------------------------------------------------
GOAL: "create a brand-new element and insert it without breaking
anything," styled to match (T11).

WHAT ALREADY EXISTS: insert (act.ts) with position options, cloneNode
reversal (F3), insert-replay continuity (PHASE5, 8/8), heal, design
snapshot for styling context. This phase is a quality phase, not a new
capability.

IMPLEMENTATION
1. One act shape: model provides {html, css, target, position} in a
   single insert call (css scoped to the inserted root's data-rv-id
   attribute — the cascade applies to the subtree only, rule 8).
2. Prompt: inserted UI must inherit the DESIGN snapshot (palette, type,
   surface language) unless the user asked for a contrasting style —
   the T11 rule, one prompt paragraph, no new machinery.
3. Constraints in the insert tool (already partially there): no inline
   event handlers, no external fetches in inserted HTML, styles
   USER-origin so reversal = removeCSS + node removal.
4. diffVisual (R1) covers inserted nodes automatically (they're in the
   sampled subtree).

TESTS: insert a summary panel on Wikipedia (dark + light + magazine-
themed variants of the same page — the T11 test: same component, three
visual systems, must adapt); reversal byte-identical; replay after
reload; a deliberate breaking-insert case (fixed-width panel) caught by
the responsive gate.

----------------------------------------------------------------------
PHASE R5 — MEDIA LAYOUT (user-requested gap #2, CSS-scoped)
----------------------------------------------------------------------
GOAL: images and videos reshape correctly — sizing, aspect, grid,
margins, captions — as part of layout transformations.

SCOPE: CSS-only (the browser does browser work). Media elements are
inventory regions (perceive already tags MEDIA) — ensure describePage
exposes media cluster geometry so the model can reason about feeds/
galleries. Test: "make this gallery 2-up with bigger images" style
requests on Wikipedia commons/article pages.

EXPLICITLY NOT IN MVP: 3D elements, WebGL scenes, video players as
components. Those are insert+script = BEHAVE tier, require a scripting
capability with its own safety review, and belong after the MVP proves
the core loop. Named, not hidden.

----------------------------------------------------------------------
PHASE R6 — RESUME T6-T8 WITH THE NEW BRAIN
----------------------------------------------------------------------
With R0-R3 in place, finish the transformation-quality roadmap on the

PHASE R7 — PRODUCT SHELL (preview / save / share — after the demo works)

What Mirage has that we lack, built last because it's worthless on a

======================================================================
3. WHAT THIS PLAN WILL NOT BUILD (named, per the rules)
======================================================================
- No architecture rewrite, no loop rewrite, no new DSL/solver/pipeline.
- No screenshot-to-model feedback in production (structural only). Any
  change to that rule is an explicit decision, separately.
- No multi-site generality work until the one-site benchmark passes.
- No 3D/WebGL, no video-player components, no workflow/keyboard-first
  systems in MVP (BEHAVE tier, post-MVP).
- No speed optimization of local code — it is not the bottleneck (B3).
- No new perception fields without a consumer (the T1 rule stays).

======================================================================
5. HOW TO KNOW THIS PLAN IS WORKING (kill criteria)
======================================================================
- R0 winner cuts calls-to-done by >50% vs T5/T6 baselines, or D1c opens.
- R1 makes the no-op class impossible to ship (both known repros dead).
- R3 8/10 by eye is the only gate that matters. If two brains and closed
  eyes still can't reach it, the problem is the architecture and we stop
  and re-diagnose — with this benchmark as the evidence, not a feeling.

Everything above is designed so that each phase is reversible and
nothing touches the proven foundation. The dream didn't fail; it was
running on a weak brain with its eyes closed.
